X and y must have compatible shapes because each row of X describes the same observation as the matching entry of y, so the number of rows in X must equal the length of y. If the counts differed, some observations would have predictors but no response, or a response but no predictors, and the model could not compare its predictions to the data. Going forward, compatible shapes are also needed for the computation itself: X @ beta requires the columns of X to match the length of beta, and the residuals y - X @ beta require both vectors to have length n.

The intercept column of ones lets the model estimate a baseline level (the predicted price when all standardized predictors are at their means or held constant) instead of forcing the fitted surface through the origin. Standardizing put all three predictors on a common scale with mean 0 and standard deviation 1, so their coefficients can be compared directly. Broadcasting makes this standardization possible without a loop because NumPy stretches the vectors means and sds, which each contain three values (one per predictor), across every row of the predictors matrix, so (predictors - means) / sds is applied to each column at once bringing out the standardized matrix Z.

X @ beta_hat is the matrix product of the design matrix and the coefficient vector, so each entry is the model’s fitted (predicted) price for one house: the intercept plus each standardized predictor times its coefficient. When an intercept is present, least squares forces the residuals to be orthogonal to the column of ones, which means they sum to zero, so the residual mean is near zero up to floating-point error. RMSE summarizes the typical size of the residuals, in the same units as the response (thousands of dollars). Finally, X * beta_hat multiplies element by element, broadcasting the vector beta_hat, which contains four values (one per column of X), down every row of X and returning a (130, 4) array, while X @ beta_hat does a matrix product that sums across the columns and returns one fitted value per observation, a (130,) array which is the model’s predicted price for each house, in thousands of dollars.

Part 5 — Reproducibility and Numerical-Computing Reflection

Clean execution matters for a computational report because it ensures that the analysis is accurate, reproducible, and reliable: anyone can rerun the file from top to bottom and regenerate every number from the data and code. Without it, a report can look correct while depending on cells run out of order or values defined by hand. Rendering from a clean session proves that the report depends only on what is written in the file. Reusable code should not depend on hidden notebook state because it makes the code unreliable and harder to reuse. If cells are executed out of order, a notebook may appear to work correctly while relying on values that exist only in the current session, such as a variable created in a cell that was later edited or deleted. Therefore, anyone running the notebook from a clean start may encounter errors or obtain different results. This creates reproducibility problems and makes the code unreliable and difficult to reuse.

In ordinary numerical work, np.linalg.lstsq() is preferable to manually computing \((X^\top X)^{-1}X^\top y\) because it is more numerically stable and avoids explicitly calculating the inverse of a matrix. Forming \(X^\top X\) squares the condition number, and matrix inversion can amplify numerical error. The least-squares function instead solves the problem directly from a stable factorization of X, so it gives more reliable coefficients. Similarly, np.allclose() is preferable to exact equality when checking QR and SVD reconstruction because floating-point computations lead to small rounding errors. Even when a reconstruction is done correctly, the computed values may differ slightly by tiny amounts. So an exact check could show a mismatch in values even though the reconstruction is correct. np.allclose() checks whether the values are sufficiently close within specified tolerances rather than requiring exact equality. The condition-number comparison taught me that the scale and magnitude of data can influence numerical stability. The raw design matrix had a condition number of about 10,733, compared with 2.73 after standardization, because variables measured on very different scales can produce poorly conditioned matrices, making numerical calculations more sensitive to small errors. A large condition number therefore does not by itself show that predictors are redundant, so examining condition numbers is an important diagnostic practice that should be read alongside the singular values when considering whether rescaling variables is necessary.
